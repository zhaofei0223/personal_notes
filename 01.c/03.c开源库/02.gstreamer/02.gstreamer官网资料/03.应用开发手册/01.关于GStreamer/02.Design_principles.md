# 设计原则

## Clean and powerful

GStreamer 提供了一个简洁的接口，用于：

- 对于想要构建媒体管道的应用程序员来说，他们可以使用一套功能强大的工具来创建媒体管道，而无需编写任何代码。执行复杂的媒体操作也变得非常容易。
- 插件程序员。GStreamer 为插件程序员提供了一个简洁易用的 API，方便他们创建独立的插件。此外，GStreamer 还集成了完善的调试和追踪机制，并提供了一系列丰富的实际插件示例。

## Object oriented

GStreamer遵循GObject对象模型。熟悉或了解GStreamer的GLib 2.0程序员会很容易上手。GLib 2.0GTK+

GStreamer 使用信号和对象属性的机制。

运行时可以查询所有对象，以获取其各种属性和功能。

GStreamer 的编程方法与 . 类似GTK+。这包括对象模型、对象所有权、引用计数等。

## Extensible

所有 GStreamer 对象都可以使用继承方法进行扩展GObject。

所有插件均动态加载，并且可以独立扩展和升级。

## Allow binary-only plugins

插件是运行时加载的共享库。由于插件的所有属性都可以通过GObject属性设置，因此无需（实际上也无法）为插件安装任何头文件。

我们特别注重使插件完全独立运行。插件的所有相关方面都可以在运行时查询。

## High performance

获得高性能的途径是：

- 使用 GLib 的GSlice分配器
- 插件之间的连接极其轻量级。数据可以在管道中以极低的开销传输。在典型的管道中，插件之间的数据传递仅涉及指针解引用。
- 提供了一种直接操作目标内存的机制。例如，插件可以直接写入 X 服务器的共享内存空间。缓冲区也可以指向任意内存，例如声卡的内部硬件缓冲区。
- 引用计数和写时复制最大限度地减少了 memcpy 的使用。子缓冲区有效地将缓冲区分割成易于管理的小块。
- 专用的流式线程，调度由内核处理。
- 通过使用专用插件实现硬件加速。
- 使用包含插件规范的插件注册表，以便延迟插件加载，直到实际使用插件为止。

## Clean core/plugins separation

GStreamer 的核心本质上与媒体无关。它只了解字节和块，并且只包含基本元素。GStreamer 的核心甚至功能足够强大，可以实现像 cp 这样的底层系统工具。

所有媒体处理功能都由核心程序外部的插件提供。这些插件告诉核心程序如何处理特定类型的媒体。

## Provide a framework for codec experimentation

GStreamer 还希望成为一个简单的框架，编解码器开发人员可以在这里尝试不同的算法，从而加快开源免费多媒体编解码器（如Xiph.Org 基金会开发的Theora 和 Vorbis）的开发。
