# Bus

总线是一个简单的系统，它负责将来自流式线程的消息转发到应用程序自身的线程上下文中。总线的优势在于，即使 GStreamer 本身是高度线程化的，应用程序也无需了解线程即可使用 GStreamer。

每个管道默认都包含一个总线，因此应用程序无需创建总线或其他任何内容。应用程序唯一需要做的就是在总线上设置一个消息处理程序，这类似于为对象设置信号处理程序。主循环运行时，系统会定期检查总线是否有新消息，并在有新消息时调用回调函数。

## 如何使用 Bus

乘坐公交车有两种不同的方式：

- 运行 GLib/Gtk+ 主循环（或者定期手动迭代默认的 GLib 主上下文），并监听总线。这样，GLib 主循环就会检查总线上是否有新消息，并在有消息时通知您。通常情况下，你会使用gst_bus_add_watch ()或 gst_bus_add_signal_watch ()在这种情况下使用。要使用总线，请使用 `addMessageHandler` 将消息处理程序附加到管道的总线上gst_bus_add_watch ()。每当管道向总线发出消息时，都会调用此处理程序。在此处理程序中，检查信号类型（参见下一节）并执行相应的操作。处理程序的返回值应为 `true`TRUE以保持其与总线的连接，返回 `false`FALSE则将其移除。

- 自行查看公交车上的留言。可以使用 gst_bus_peek ()and/or 命令来完成此操作gst_bus_poll ()。

```c
#include <gst/gst.h>

static GMainLoop *loop;

static gboolean
my_bus_callback (GstBus * bus, GstMessage * message, gpointer data)
{
  g_print ("Got %s message\n", GST_MESSAGE_TYPE_NAME (message));

  switch (GST_MESSAGE_TYPE (message)) {
    case GST_MESSAGE_ERROR:{
      GError *err;
      gchar *debug;

      gst_message_parse_error (message, &err, &debug);
      g_print ("Error: %s\n", err->message);
      g_error_free (err);
      g_free (debug);

      g_main_loop_quit (loop);
      break;
    }
    case GST_MESSAGE_EOS:
      /* end-of-stream */
      g_main_loop_quit (loop);
      break;
    default:
      /* unhandled message */
      break;
  }

  /* we want to be notified again the next time there is a message
   * on the bus, so returning TRUE (FALSE means we want to stop watching
   * for messages on the bus and our callback should not be called again)
   */
  return TRUE;
}

gint
main (gint argc, gchar * argv[])
{
  GstElement *pipeline;
  GstBus *bus;
  guint bus_watch_id;

  /* init */
  gst_init (&argc, &argv);

  /* create pipeline, add handler */
  pipeline = gst_pipeline_new ("my_pipeline");

  /* adds a watch for new message on our pipeline's message bus to
   * the default GLib main context, which is the main context that our
   * GLib main loop is attached to below
   */
  bus = gst_pipeline_get_bus (GST_PIPELINE (pipeline));
  bus_watch_id = gst_bus_add_watch (bus, my_bus_callback, NULL);
  gst_object_unref (bus);

  /* [...] */

  /* create a mainloop that runs/iterates the default GLib main context
   * (context NULL), in other words: makes the context check if anything
   * it watches for has happened. When a message has been posted on the
   * bus, the default main context will automatically call our
   * my_bus_callback() function to notify us of that message.
   * The main loop will be run until someone calls g_main_loop_quit()
   */
  loop = g_main_loop_new (NULL, FALSE);
  g_main_loop_run (loop);

  /* clean up */
  gst_element_set_state (pipeline, GST_STATE_NULL);
  gst_object_unref (pipeline);
  g_source_remove (bus_watch_id);
  g_main_loop_unref (loop);

  return 0;
}
```

需要注意的是，处理程序将在主循环的线程上下文中调用。这意味着管道和应用程序之间通过总线进行的交互是异步的，因此不适用于某些实时应用，例如音频轨道之间的交叉淡入淡出、（理论上的）无缝播放或视频特效。所有这些操作都应该在管道上下文中完成，最简单的方法是编写 GStreamer 插件。不过，它对于其主要用途——将消息从管道传递到应用程序——非常有用。这种方法的优势在于，GStreamer 内部执行的所有线程操作对应用程序都是隐藏的，应用程序开发人员完全不必担心线程问题。

请注意，如果您使用的是默认的 GLib mainloop 集成，则可以不附加监视，而是连接到总线上的“message”信号。这样，您无需switch()监视所有可能的消息类型；只需连接到感兴趣的信号，格式为 `<message>` message::<type>，其中<type>`<message>` 是特定的消息类型（有关消息类型的说明，请参见下一节）。

上述代码片段也可以写成：

```c
GstBus *bus;

[..]

bus = gst_pipeline_get_bus (GST_PIPELINE (pipeline));
gst_bus_add_signal_watch (bus);
g_signal_connect (bus, "message::error", G_CALLBACK (cb_message_error), NULL);
g_signal_connect (bus, "message::eos", G_CALLBACK (cb_message_eos), NULL);

[..]
```

如果您未使用 GLib 主循环，则默认情况下异步消息信号将不可用。但是，您可以安装一个自定义同步处理程序，该程序会唤醒自定义主循环并使用它 gst_bus_async_signal_func ()来发出信号。（详情请参阅 文档 ）

## 消息类型

GStreamer 预定义了一些可通过总线传递的消息类型。不过，这些消息类型是可扩展的。插件可以定义额外的消息，应用程序可以选择为这些消息编写特定的代码，也可以选择忽略它们。强烈建议所有应用程序至少通过向用户提供视觉反馈来处理错误消息。

所有消息都包含消息源、类型和时间戳。消息源可用于查看哪个元素发出了该消息。例如，对于某些消息，大多数应用程序可能只关注由顶层管道发出的消息（例如，状态更改通知）。以下列出了所有消息，并简要说明了它们的功能以及如何解析消息的特定内容。

- 错误、警告和信息通知：这些通知用于元素向用户显示有关管道状态的消息。错误消息是致命的，会终止数据传递。必须修复错误才能恢复管道活动。警告消息虽然不是致命的，但也表明存在问题。信息消息用于通知非问题。所有这些消息都包含一个GError包含主要错误类型和消息的字符串，以及可选的调试字符串。可以使用 `getError()` 和 `getDebug()` 提取错误 gst_message_parse_error()和_parse_warning ()调试字符串。_parse_info ()错误字符串和调试字符串在使用后都应释放。

- 流结束通知：当流结束时发出此通知。管道状态不会改变，但后续的媒体处理将会暂停。应用程序可以使用此通知跳到播放列表中的下一首歌曲。流结束后，也可以在流中回溯播放。播放将自动继续。此消息没有特定参数。

- 标签：当在流中找到元数据时发出。对于同一管道，标签可能会多次发出（例如，一次用于描述性元数据，如艺术家姓名或歌曲标题；另一次用于流信息，如采样率和比特率）。应用程序应在内部缓存元数据。gst_message_parse_tag()应使用 `get_taglist()` 函数解析标签列表，并gst_tag_list_unref ()在不再需要时将其删除。

- 状态变更：在状态变更成功后发出。 gst_message_parse_state_changed ()可用于解析此次转换的旧状态和新状态。

- 缓冲：在网络流缓存期间发出。可以通过从返回的结构体中提取“buffer-percent”属性，手动从消息中提取进度（以百分比表示）gst_message_get_structure()。另请参阅缓冲。

- 元素消息：这些是特定元素独有的特殊消息，通常代表附加功能。元素的文档应详细说明该元素可能发送哪些元素消息。例如，如果流包含重定向指令，QuickTime 解复用器元素“qtdemux”在某些情况下可能会发送“redirect”元素消息。

- 应用程序特定消息：可以通过获取消息结构（见上文）并读取其字段来提取有关这些消息的任何信息。通常可以安全地忽略这些消息。

应用程序消息主要用于应用程序内部，以便在应用程序需要将信息从某个线程传递到主线程时使用。这在应用程序使用元素信号时尤其有用（因为这些信号将在流式线程的上下文中发出）。
